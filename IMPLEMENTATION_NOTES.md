# IgniteX DB + Check-in Changes

## Database

Run the existing migrations first, then run:

`supabase/migrations/004_registration_reporting_checkin.sql`

This migration adds:

- `participant_event_registrations` — plaintext admin reporting table with registration ID, participant name, and event name, one row per event registration.
- `event_registration_counts` — per-event registered / approved / checked-in counters.
- `campus_checkins` — explicit campus-entry record. The verification method is locked to `QR_SCAN`.
- `IGX-XXXX` registration IDs for new registrations and conversion of legacy registration IDs.
- Triggers that keep participant/event reporting and event counters synchronized.

## Registration ID

New registration IDs are generated by the database and have the exact format:

`IGX-XXXX`

The four characters are uppercase alphanumeric characters. The database checks for collisions.

## Gate check-in flow

1. Staff opens **Gate Ticket Scanner**.
2. Click **SCAN QR WITH CAMERA** and allow camera permission.
3. The browser's QR detector reads the QR pass.
4. The server verifies the QR/token and displays the participant and events.
5. Staff clicks **CHECK-IN PARTICIPANT**.
6. Only then is the registration changed to `CHECKED_IN` and a `campus_checkins` record is created.
7. A second scan returns `ALREADY_CHECKED_IN`.

The scanner also accepts the raw QR token, the approval QR URL, the verification code, or the `IGX-XXXX` registration ID as a manual fallback.

## Important

The reporting table is plaintext by design for admin reporting. Payment screenshots, transaction information, QR secrets, and verification plaintextes are not copied into that table.

If the Supabase Edge Functions are deployed separately, redeploy the updated `register` and `verify-registration` functions after applying migration 004.

## Database transparency

Participant names, event names, registration IDs, verification codes, and QR tokens are stored directly as plaintext columns. No verification-code hash/encryption layer is used. PostgreSQL RLS still controls which application roles can read the tables; RLS is access control, not encryption.
